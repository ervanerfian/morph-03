## Current milestone

The PHP Native application foundation is in the open PR. A Morph-authored Twig application shell and an explicitly non-authenticated foundation preview are now implemented. The UI uses original Morph markup/styles and a small TypeScript ES module for responsive navigation; all supplied HTML, PHP, and Symfony UI variants remain untouched as reference material. Data-engine work remains design-only. The developer has selected schema-level Field Binding owned by canonical Data Source ID, explicit references from distinct Table IDs—each scoped to one Database—to the same Data Source (sharing Records/schema without automatically granting access), and a Database-copy policy that forks each unique Data Source once with schema/Records under new IDs while leaving the original sources unchanged. Field Definition IDs are reused when semantics/config match; different semantics require a distinct ID/config. Forked schema membership gets a new binding UUID, while the original binding ID is not reused. How schema revisions pin these IDs, handling of external or non-copied Relation targets, and permission transfer remain open; internal edges whose endpoints are both copied are remapped to the copied target. No access is implied. Other selected decisions are separate Table View presentation, `field_definition_id` as the canonical V1 Field-value identity, single-target Relation per source Record/Field, no reverse Relation Field in V1, target Trash blocked by incoming edges, permanent delete blocked until all incident edges are resolved, and scoped non-superuser `morph03_app` for PHP runtime. These decisions are documented; they do not approve or imply schema DDL, role creation, grants, or local credential changes.

## Decisions and blockers

The developer selected `morph03_app` as the scoped, non-superuser PHP runtime role; the 2026-11-02 read-only catalog check found that role absent, so its attributes and privileges were not available. The same check confirmed `morph03_admin` is a superuser that bypasses RLS; it must not be used in PHP's `DATABASE_URL`. No role creation, grants, DDL, or credential configuration has been performed. Do not provision a role or grant privileges without explicit authorization and review of the least-privilege plan.

Relation semantics confirmed by the developer: each config chooses exactly one target Display Field, and each source Record/Relation Field has at most one target Record in V1. Different source Records may reference the same target; target uniqueness is not implied. The target `record_id` is immutable and belongs to each edge, not Relation config. Field Binding belongs to the canonical Data Source schema via `data_source_id`; Table View controls only visibility, order, and label. Each Table identity belongs to exactly one Database; distinct Tables in different Databases may explicitly reference the same Data Source ID and share Records/schema, but the reference grants no access. Copying a Database forks each unique referenced Data Source once and copies schema/Records to new IDs; the original sources and other references remain unchanged. Field Definition IDs are reused when semantics/config match; different semantics require a distinct ID/config. Forked schema membership gets a new binding UUID; how revisions pin it, external or non-copied Relation target mapping, and permission transfer remain open. Internal edges whose endpoints are both copied remap to the forked target. Ownership, permission, and revision policy for a shared Data Source also remain open. Multi-field Projection, multi-target Relation, and reverse Relation Fields are not part of V1. The canonical key for scalar values and Relation edges is `field_definition_id`; a reused Field Definition means the same semantics/config, while different per-Data-Source semantics require explicit distinct identity/config. A target Record with incoming edges cannot be trashed; permanent delete is blocked while any incoming/outgoing edge remains, with no implicit cascade. Source Record/Database Trash, retention, and inaccessible-target UI remain open.

`DATASTAR-NATIVE-WEB-GUIDANCE.md` is the source of truth for Datastar-first and native-browser interaction policy. The developer's Modern PHP Super Apps Stack explicitly includes Node/npm for TypeScript compilation and testing; current `tsc` output is native browser ESM with no bundler. Working interpretation: “native ESM/no-build” means no bundled SPA/client runtime, while the TypeScript-to-ESM compile step remains allowed. No tooling change was made. The developer clarified the stack list is a general picture and Morph continues with PostgreSQL 18; do not infer a MySQL/SQLite multi-driver requirement from that overview. `INTRODUCTION.md`'s older PostgreSQL/SQLite runtime examples have been aligned to this project decision. The guide's external references have not been independently reviewed from the sandbox.
